Validate and rebase onto `main`. Target branch: $ARGUMENTS

Current branch: !`git branch --show-current`
Branches: !`git branch -vv`

If the current branch is `main`, the branch to rebase must be given as an argument — **if it wasn't, stop and ask for it.** If already on a non-main branch, that's the one being rebased.

These branches were generated by AI some time ago. The default assumption is that they may be stale, superseded, or wrong — validating is the point of this command, rebasing is just the follow-through.

## 1. Is this work still needed?

- `git log main..<branch>` — what does it actually contain?
- `git log <branch>..main` — what has happened since?
- Was the same problem already solved on `main` by another change? Has the code it touches been restructured or deleted?

**If the work is redundant, superseded, or carries high regression risk, stop and report that.** Deleting a branch nobody needs is a better outcome than a clean rebase of dead code. Don't rebase on autopilot.

## 2. Rebase

Rebase onto the latest `main` and resolve conflicts. When resolving, favour `main`'s current structure — the branch's assumptions about file layout are the stale part.

## 3. Review the result

Read the rebased diff as if it were new code. It was written against an older codebase, so check it still honours current invariants: Mission Control isolation, 300-line files, the performance checklist, the current design tokens. Fix what drifted.

For anything substantial, run `/devils-advocate` over the rebased diff.

## 4. Verify

```
npm run test:unit
npm run lint
npm run tsc
```

**Failing tests after a rebase are a high-risk signal, not a chore.** They usually mean the branch's assumptions no longer hold. Report the failures and let the user decide whether to fix forward or drop the branch — don't quietly patch tests to make them pass.
